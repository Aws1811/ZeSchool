# Parent-Teacher Connection Platform

## Project Description

The Parent-Teacher Connection Platform is a full stack digital system
designed to improve communication, coordination, and information sharing
between parents and teachers.

The platform brings communication, academic information, reports,
schedules, transportation information, AI-assisted analysis, and
optional smartwatch data into one centralized environment. Its core
relationship is between the parent and the teacher.

Students do not have accounts, login access, or dashboards. A child is
represented as a data entity connected to the parent's account and to
the academic records managed by authorized teachers.

## Project Goal

The project aims to reduce fragmented communication between families and
schools by giving parents and teachers a shared system for accessing
relevant information about a child.

The main goals are to:

- Improve direct communication between parents and teachers.
- Centralize academic and school-related information.
- Make grades and reports easier for parents to understand.
- Provide organized access to calendar events and transportation
  information.
- Use AI to analyze authorized information and provide useful
  summaries, patterns, and recommendations.
- Give parents a centralized view of information related to their
  child.
- Explore secure integration with a child-connected smartwatch for
  financial, activity, location, and health-related information when
  those features are enabled.
- Protect academic, financial, location, and health-related
  information through strong authentication and authorization.

## Main Features

### Parent and Teacher Messaging

The dashboard acts as the main communication area. Parents and teachers
can communicate through conversations that remain available as
conversation history.

Messages can focus on academic progress, school activities, reports,
schedules, transportation, and other information relevant to the child.

### Calendar

The calendar centralizes important dates such as:

- Exams
- Meetings
- School events
- Assignments and deadlines
- Parent-teacher meetings
- Important announcements

Authorized teachers can add relevant events, while parents can view
events associated with their child.

### Bus and Map Information

The transportation area can present available school bus and route
information, including:

- Bus information
- Current bus location when available
- Route information
- Pickup and drop-off locations
- Map visualization
- Estimated arrival information when supported by the transportation
  data source

### Grades

The grades area presents academic performance information connected to
the child, such as:

- Subject grades
- Assessment results
- Grade history
- Performance trends
- Overall academic performance

### Reports

The reports area organizes reports created or shared by teachers and
reports generated by the system. Examples include:

- Academic reports
- Attendance-related reports when attendance data is available
- Teacher observations
- Progress reports
- General school reports

### AI Analysis

AI is integrated as an assistant that works with authorized platform
data. It is not intended to be a generic chatbot and must not make final
decisions on behalf of parents or teachers.

The AI can support:

- Academic performance analysis
- Grade trend analysis
- Identification of significant changes in performance
- Report summaries
- Parent-teacher communication summaries
- Understandable explanations of academic information
- Recommendations based on available information
- Identification of patterns that teachers may want to review

Only data required for a specific AI request should be sent to the AI
service.

### Optional Smartwatch Integration

The platform may integrate with a smartwatch connected to the child. The
child still does not receive a platform account.

When enabled and authorized, the smartwatch integration may provide:

- Activity information
- Health-related information
- Spending information
- Balance information
- Purchase history
- Location-related information
- Summaries based on collected device data

## User Roles

### Parent

A parent can:

- Register and log in.
- Access information only for a child they are authorized to view.
- Communicate with teachers.
- View conversation history and notifications.
- View calendar events.
- View bus and map information when available.
- View grades and reports.
- Request AI-assisted analysis of authorized information.
- Review permitted smartwatch information when smartwatch integration
  is enabled.

### Teacher

A teacher can:

- Log in to the platform.
- Communicate with authorized parents.
- Share academic information.
- Provide grades.
- Create or review reports.
- Add relevant calendar events.
- Share transportation-related information when applicable.
- Use AI-assisted analysis to review academic performance and
  patterns.

### Child

The child is a domain entity, not a system user.

There is no student account, student login, student role, or student
dashboard. Child records connect the parent's account with academic,
reporting, transportation, and optional smartwatch information.

## AI Features

The AI layer should be context-aware and permission-aware.

A typical request follows this process:

1.  A parent or teacher submits an AI-related question.
2.  The backend verifies authentication.
3.  The backend verifies the user's role and access to the relevant
    child.
4.  The backend retrieves only the necessary authorized information.
5.  The backend prepares a limited context containing relevant grades,
    reports, messages, calendar data, or other permitted records.
6.  The necessary context is sent to the AI service.
7.  The AI returns an analysis, summary, explanation, or recommendation.
8.  The backend returns the result to the authorized user.
9.  The system may store an AI analysis record when required for
    history, auditing, or product functionality.

AI output is advisory. Parents and teachers remain responsible for
decisions and actions.

## Smartwatch Features

Smartwatch integration is optional and should be isolated from the core
parent-teacher functionality so that the platform can operate without
it.

### Financial Tracking

When enabled, the system may track:

- Current balance
- Amount spent
- Purchase history
- Purchase locations
- Spending categories
- Remaining balance
- Spending patterns

A parent-facing spending summary may present:

- Current Balance
- Total Spent This Week
- Recent Purchases
- Most Common Spending Category
- Spending Locations
- Spending Trend

AI may summarize spending patterns using only authorized financial
records.

### Health and Activity Tracking

When appropriate and explicitly enabled, the smartwatch may provide
health-related or activity information. This information is private and
must only be visible to users who have explicit authorization to access
it.

### Location Information

Location information must only be collected or displayed when the
location feature is explicitly enabled and the user has appropriate
authorization.

## System Architecture

The application is organized into the following major components:

### Frontend

Responsible for:

- Landing, authentication, dashboard, calendar, bus/map, grades,
  reports, and AI analysis interfaces
- Displaying authorized data
- Collecting user input
- Sending requests to the backend API
- Presenting messages, notifications, analysis results, and optional
  smartwatch information

The frontend should not determine authorization by itself. Access
decisions must be enforced by the backend.

### Backend API

Responsible for:

- Authentication
- Authorization and role checks
- Parent-child and teacher-child access validation
- Business logic
- Messaging operations
- Academic data operations
- Calendar operations
- Transportation data access
- AI context preparation
- Smartwatch data processing when enabled
- Secure communication with external services

### Database

Stores structured platform information such as users, parent and teacher
profiles, children, relationships, messages, grades, reports, events,
transportation data, AI analysis records, and optional smartwatch
records.

### Authentication and Authorization

Controls identity and access. Every protected request should be checked
on the server before data is returned or modified.

### AI Service

Receives only the minimum authorized context required for a specific
analysis and returns an advisory response.

### Optional Smartwatch Integration

Receives permitted device data and associates it with the correct child
record without creating a student login.

### Optional Map and Transportation Service

Provides map visualization, route information, location information, and
estimated arrival data when those services are configured.

## Database Overview

A relational database can model the platform clearly while preserving
the distinction between users and children.

Possible entities include:

- `Users`: authentication identity and shared user fields.
- `Parents`: parent-specific profile data linked to a user.
- `Teachers`: teacher-specific profile data linked to a user.
- `Children`: child records with no authentication credentials.
- `ParentChild`: relationships defining which parent can access which
  child.
- `TeacherChild` or an equivalent class/enrollment relationship:
  defines which teachers are authorized to work with a child.
- `Conversations`: parent-teacher conversation containers.
- `Messages`: individual messages within conversations.
- `Grades`: subject and assessment results associated with a child.
- `Reports`: teacher-created or system-generated reports.
- `CalendarEvents`: school dates and events.
- `BusRoutes`: transportation route information.
- `Locations`: permitted transportation or smartwatch location
  records.
- `AIAnalysisRecords`: AI request metadata and/or stored results where
  appropriate.
- `SmartwatchDevices`: registered device information connected to a
  child.
- `Purchases`: smartwatch-related purchase records.
- `Balances`: current or historical financial balance data.
- `HealthData`: permitted health or activity records.

The exact schema should be finalized according to the selected backend,
database technology, and school data model.

## Authentication and Security

Security is a core requirement because the platform can contain
information about children.

The implementation should include:

- Secure authentication for parents and teachers.
- Secure password hashing and storage.
- Role-based access control.
- Server-side authorization on protected endpoints.
- Parent-child relationship checks.
- Teacher access checks based on valid relationships or assignments.
- Protection against access to another child's information.
- Secure handling of academic information.
- Additional protection for financial, location, and health-related
  information.
- Validation and sanitization of incoming data.
- Secure session or token handling according to the selected
  authentication method.
- Minimal disclosure of data to the AI service.
- Protection of AI endpoints from unauthorized requests.
- Careful logging that avoids exposing sensitive data.

## Project Workflow

A typical parent workflow is:

1.  The parent registers or logs in.
2.  The backend authenticates the account.
3.  The system loads children connected to that parent.
4.  The parent opens the dashboard and communicates with an authorized
    teacher.
5.  The parent can navigate to calendar, transportation, grades, or
    reports.
6.  The parent can request AI analysis of information they are permitted
    to access.
7.  If smartwatch integration is enabled, the parent can review
    authorized device information.

A typical teacher workflow is:

1.  The teacher logs in.
2.  The backend authenticates the account and identifies the teacher
    role.
3.  The system provides access only to children and parents connected to
    the teacher's authorized academic context.
4.  The teacher communicates with parents, manages permitted academic
    information, creates or reviews reports, and adds relevant events.
5.  The teacher can request AI analysis of authorized academic data.
6.  Any change is validated and stored through protected backend
    endpoints.
